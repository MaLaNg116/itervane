# P0 评测材料

`cases.json` 包含 24 个可重复场景的输入、预期和独立判定依据：开发交付 8 个、运维 6 个、治理 6 个、知识沉淀 4 个；其中 6 个单列为 holdout。

当前实现的是**材料准备检查和可信基线验证**。`pnpm probe:evaluation` 验证清单、唯一 ID、场景覆盖、固定源码变异是否仍匹配基线，然后真实构建和测试标准应用。它不会执行变异代码、发布应用或把 24 个平台场景记为通过。源码变异只在内存中检查，未来只能在专用虚拟机中执行。

输入分为四类：

- `baseline`：标准应用原样。
- `source-edit`：基线相对路径和精确替换，必须唯一匹配；同一案例内按顺序叠加。
- `environment`：只允许标准应用的模式和版本变量，在任务隔离环境中注入。
- `scenario`：未来测试驱动器的结构化事件序列；当前没有解释执行器，也不把这些记录当真实下游证据。

每次后续评测都应固定 Git 快照、输入变异、规则版本、模型配置、预算和随机种子，单独保存实际结果与产物引用。`expected` 是 oracle 要求，不能写入实际结果或被 Agent 自报成功替代；缺少前置条件应记录未执行或阻塞。

holdout 不用于提示词和规则候选调优。公开仓库中的 split 是流程约束，不保证数据从未被模型见过；正式评测时由独立驱动器保管预期、受保护检查及 holdout 输入，不挂载到修复工作区。后续新增真正独立的样例，防止只记住这批案例。

含“拒绝”“阻断”的案例针对恶意请求或错误候选；不能简单把整个任务失败率当作 Agent 质量。评测既检查越权动作没有发生，也检查合法任务仍能完成。D02—D04 留有确定性修复对照，后续与 Agent 使用相同复验与资源上限比较。

P1—P5 按清单中的阶段接入正式任务、真实扫描器、MCP、审批、操作核对和规则复用。P0 的数据库或协议单测只覆盖部分机制，不能代替对应平台端到端验收。
