## 3. TS、数据库与并发的已确认落地

### 3.1 主技术栈

门户、控制面、后台 Worker、Agent Harness 与 MCP 采用 TypeScript；主运行时为 Node.js。保留 API、Worker、Runner 的进程与权限边界。第三方工具采用其原生运行方式，不为了统一语言重写扫描器或部署平台。

首期数据访问采用 PostgreSQL + Drizzle + node-postgres，调度采用 pg-boss，Agent 执行基础采用 LangGraph TS。具体兼容版本、协议和镜像 digest 在 P0 验证后锁定。框架文档中的示例或版本号不是已通过验证的组合。

模型接入按用户在实施时确认的补充支持 Anthropic 和 OpenAI 两种协议适配器；首轮验证 Anthropic 协议，每个任务只使用明确选择的一种协议和模型，不在失败时静默切换。兼容协议不等于厂商官方认证或某个模型已通过工具调用验证。

### 3.2 三类持久化各有责任

| 组件 | 负责 | 不承担的替代责任 |
|---|---|---|
| 平台领域记录 | 任务阶段、有效执行权、候选、授权、正式操作结果和证据 | 不把模型总结当事实 |
| pg-boss | 持久化调度、领取、重试、延迟及唤醒 | 队列完成不代表业务成功，也不另建一套业务工作流 |
| LangGraph checkpointer | 角色图执行状态、上下文及恢复进度 | 检查点不能授予部署或运维权限 |

MVP 可在同一平台数据库内分 schema，分别管理迁移和权限。长日志、源码包、补丁、报告及镜像使用相应产物存储，领域表保留关联与摘要。第三方服务的内部存储独立维护，不直接读写其私有表。

批准决定、唯一逻辑操作及入队保持事务原子性；具体适配由 P0 验证。领域提交、图检查点和远端操作并非一个分布式原子事务，恢复时必须核对它们的实际记录。

### 3.3 串行基线下仍要正确处理竞争

- 同时只有一个正在执行的业务工作流；该限制是全局总量，不能只在每个队列各设置为一而导致多条工作流并行。
- 一个 run 和一个可写修复工作区只有一个有效执行者。执行代次失效后，旧执行者不得继续提交正式结果或发起新工具操作。
- 同一应用环境的发布、重启、回滚统一协调；结果未知时阻止新的冲突变更，先进行实际状态核对。
- 等待人工、模型或外部系统时不持有长数据库事务。审批暂停释放执行槽位；需要保留的上下文和产物先持久化。
- 运维创建关联修复任务后释放相应执行槽位，避免父任务占槽等待子任务。
- 重试按错误及副作用类型决定。重复投递不会自动获得再次部署或重启的资格。
- 取消意味着停止新动作并清理环境；已发出的外部动作继续核对结果，不直接标记为已经撤回。
- API、Worker、队列、检查点的连接池统一核算。MVP 不提前扩展到多业务工作流并发或高可用。

这些条目用于落实既有串行、授权与恢复要求，不增加新的 MVP 产品范围。

## 4. Komodo 与 Kubernetes 的取舍记录

Komodo 是首个部署适配后端，Whiskers 是首个运维 MCP 集成目标。采用当前 Komodo + Docker/Compose 模式的依据，是固定目标、单镜像、无状态 Demo、人工确认以及首期不承诺高可用的范围。

当前方案管理多台服务器，不等于已经提供跨节点自动调度和故障迁移。平台不为此自研集群调度器、服务发现或跨节点故障迁移系统。

Kubernetes 保留为后续可选后端。已有成熟集群、明确的多副本与故障迁移要求、弹性与统一资源池需求，或主动纳入云原生工程目标，都可以单独触发重新评估，无需等待所有条件同时出现。个人项目也可以使用 K3s；安装成本与完整运维责任分别评估。

基础运行平台承担适合它的确定性恢复，Agent 处理诊断、处置判断、验证、关联修复及例外。不得为了展示 Agent 重启能力而人为增加日常操作。

后续增加 Kubernetes 时，五种角色、三条闭环和平台治理仍要保留。普通 Pod 或 Namespace 不能直接替代不可信代码的专用隔离边界。应用、候选与操作属于平台领域模型，下游资源 ID 作为映射管理。

## 5. 阶段完成的判定

| 阶段 | 可证明的成果 | 不能提前替代的后续成果 |
|---|---|---|
| P0 | 技术、协议、事务、隔离与原生确认有验证记录 | 不代表主平台或 Agent 闭环已完成 |
| P1 | 真实任务能够受授权运行、保存、查询、停止和恢复 | 扫描报告不等于完整 Agent 交付 |
| P2 | MCP 发起、审计修复、独立复验、人审发布和上线验证 | 不代表运维和经验复用已完成 |
| P3 | 真实 MCP 运维、获批处置、恢复验证和关联修复 | 不代表规则与 Runbook 已被后续任务复用 |
| P4 | 代码规则与 Runbook 均经验证、人审发布并在后续任务复用 | 功能闭环齐备，仍待 P5 交付验证 |
| P5 | 故障注入、重复端到端、备份恢复、干净安装与开源材料通过 | 才形成可交付的 MVP v0.1 |

阶段验收以实施计划中的完整条目为准。本表用于避免把中间里程碑误报为 MVP 已完成。

## 6. 后续变更与证据

开发变更说明应关联所实现的模块、蓝图要求和计划阶段，附相关验收证据与已知限制。模型声称成功、单次演示成功、代码已合并，都不能代替相应完成条件。
