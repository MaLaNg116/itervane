## 2. 首期收窄支持范围，保留完整闭环。

| 维度 | MVP 边界 |

| 应用状态 | 无持久化业务数据库、无业务数据库迁移 |

| 规则沉淀 | 至少一条代码规则、一条 Runbook 完成人审和后续复用 |

| 可靠性 | 持久化、预算、取消、暂停恢复、结果核对与备份恢复 |

## 3. 主技术栈采用 TS，基础设施继续复用成熟项目。

| 领域 | 首期选择 | 用法与边界 |
|---|---|---|
| 主语言与运行时 | TypeScript 严格模式、Node.js 24 LTS | API、Worker、Agent、MCP 和评测编排统一语言 |
| 仓库管理 | pnpm workspace、模块化单体 | 同仓库维护，按进程和权限部署 |
| HTTP API | Fastify | 认证接入、领域接口、任务查询、人工操作 |
| 接口契约 | Zod＋JSON Schema＋OpenAPI | 共享公开契约；入站、出站数据均校验 |
| 门户 | React 19、Vite、Ant Design 6 | 延续原方案，采用项目自身的通用设计规范 |
| Agent 运行基础 | LangGraph TS 开源库 | 复用图执行、检查点和人工中断 |
| Agent Harness | 自研领域执行框架 | 目标、上下文、工具、预算、停止、交接和恢复 |
| 模型接入 | Anthropic/OpenAI 协议适配，首轮 Anthropic | 用户实施补充：每任务明确一种协议与模型，不静默切换；实际模型能力须验证 |
| MCP | 官方 TypeScript SDK | 对外 Server、对内 Client；远程优先 Streamable HTTP |
| 业务数据库 | PostgreSQL 17 | 延续此前版本线，P0 锁定具体小版本 |
| 数据访问 | Drizzle＋node-postgres | 领域查询、事务、条件更新与必要的显式 SQL |
| 数据迁移 | Drizzle Kit＋版本化 SQL | 生成后审查，单独执行迁移 |
| 持久化队列 | pg-boss | 复用 PostgreSQL，承担入队、领取、重试、延迟和唤醒 |
| Agent 检查点 | LangGraph PostgreSQL checkpointer | 独立管理检查点表及迁移 |
| 执行隔离 | Linux、QEMU/KVM＋libvirt、一次性任务虚拟机 | 执行不可信代码、安装依赖、测试和构建 |
| 扫描与验证 | Gitleaks、Trivy、Semgrep CE、应用测试、HTTP 检查 | 扫描结果归一化；规则许可证独立核查 |
| 发布后端 | Komodo 官方 TS 客户端 | 发布、版本核对及指定版本恢复 |
| 运维后端 | Whiskers MCP 优先 | 状态、脱敏日志、指标、受控重启 |
| 身份与入口 | OIDC/OAuth、Keycloak、Traefik | 复用认证与访问保护；平台负责项目授权 |
| 产物存储 | 受管文件卷＋内容哈希；Distribution OCI Registry | 保存快照、报告、补丁及镜像 |
| 测试 | Vitest、真实 PostgreSQL 集成测试、Playwright | 关键数据库行为不使用 SQLite 替代验证 |
| 观测 | 结构化事件、日志、关联 ID、基础指标 | 首期不强制引入独立追踪平台 |
| 参考部署 | Docker Compose＋分离的执行和运行虚拟机 | 保持自托管，不引入 Kubernetes |

LangGraph TS 提供检查点与人工中断基础；正式授权和外部操作结果仍由平台领域记录管理。[LangGraph 检查点](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)

官方 MCP TS SDK 提供客户端、服务端及 HTTP 接入能力；Komodo 提供官方 TS 客户端。[MCP TS SDK](https://ts.sdk.modelcontextprotocol.io/v2/)、[Komodo API](https://komo.do/docs/ecosystem/api)

具体依赖、镜像 digest、协议版本和兼容组合在 P0 实测后锁定，不直接跟随 `latest` 或 RC 文档示例。

Komodo 的存储沿用其官方方案；严格开源参考部署优先验证 FerretDB。其 PostgreSQL＋DocumentDB 存储单独部署和维护，平台不直接读写第三方内部表。[Komodo FerretDB](https://komo.do/docs/setup/ferretdb)

## 4. 采用模块化单体，部署边界按执行责任划分。

首期部署为：

- **API 进程：** 门户接口、MCP Server、身份校验、人工确认与查询。
- **Worker 进程：** 消费任务、运行 Agent、调用受控适配器。
- **Runner 控制器：** 管理隔离环境、文件、命令、资源限制和清理。
- **第三方服务：** PostgreSQL、身份服务、Registry、Komodo、Whiskers。

Runner 控制器通过受限、参数化的系统接口管理虚拟机。Agent 可以在当前任务虚拟机内使用获准的文件和命令工具；宿主机管理接口及凭证不进入 Agent 工具集。

| 编号 | 模块 | 职责 | 主要依赖 |
|---|---|---|---|
| M01 | 身份与项目 | 用户、工作区、项目、应用、环境、资源映射及授权 | 共享契约、身份服务 |
| M02 | 任务、操作与审批 | 状态机、执行权、人工待办、操作记录、取消与恢复 | M01、数据库、队列 |
| M03 | Agent Harness | 自主循环、上下文、预算、停止及角色交接 | M02、M05、模型适配 |
| M04 | 领域 Agent | 五种角色及结构化结果 | M03、工具与证据 |
| M05 | 工具与策略网关 | 参数、权限、目标、执行代次、副作用和错误分类 | M01、M02 |
| M06 | Sandbox Runner | 虚拟机、工作区、执行、资源限制、回收 | M05、虚拟化基础 |
| M07 | 源码、产物与证据 | Git 快照、差异、报告、镜像、候选及哈希关联 | M01、M06、存储 |
| M08 | MCP 接入 | 外部 Server、内部 Client、认证和异步任务契约 | M01、M02、M05 |
| M09 | 发布适配器 | Komodo 发布、版本查询、恢复及结果核对 | M02、M05、M07 |
| M10 | 运维适配器 | Whiskers MCP、健康事件、诊断数据及受控处置 | M02、M05、M08、M09 |
| M11 | 规则与经验 | Skill、案例、规则、Runbook、验证、审核和版本 | M04、M07 |
| M12 | 门户 | 项目、任务、差异、审批、运维和规则界面 | 公开 API 契约 |

另外设置共享契约包，供 API、Worker、门户和 MCP 使用。数据库实体保持服务端内部使用，公开接口单独定义。

这些是代码模块，不拆成十三个微服务。

## 5. 数据库分别管理业务事实、队列和 Agent 检查点。

MVP 在同一个平台数据库内划分三类 schema：

| 数据区域 | 内容 | 管理方式 |
|---|---|---|
| 领域数据 | 项目、任务、审批、操作、候选、规则及事件 | 平台迁移 |
| pg-boss 数据 | 排队、领取、重试及调度信息 | pg-boss 迁移 |
| Agent 检查点 | 图状态、上下文和恢复信息 | checkpointer 迁移 |

分别管理迁移及数据库权限，运行账号不持有常驻 DDL 权限。

领域数据至少覆盖以下关系：

| 数据组 | 主要内容与关系 |
|---|---|
| 身份与资源 | 工作区 → 项目 → 应用 → 环境，以及访问成员和下游资源绑定 |
| 源码快照 | 仓库、原始 commit、修复快照、差异、模板与规则版本 |
| 任务与 Agent run | 任务类型、阶段、当前有效 run、执行代次、预算和父子任务关系 |
| 发现与证据 | 问题、位置、证据引用、置信度、覆盖限制和处置状态 |
| 候选与验证 | 源码、报告、测试、镜像 digest、配置摘要和目标环境 |
| 审批 | 请求人、确认人、本人确认标记、对象指纹、有效期、撤销及使用记录 |
| 外部操作 | 动作、目标、参数摘要、授权、下游 ID、执行尝试和核对结果 |
| 规则与经验 | 案例、Skill、规则、Runbook、样例、审核、发布与回滚版本 |
| 事件与指标 | 任务事件序号、工具调用、状态变化、耗时和成本 |

设计时固定以下约束：

- **候选冻结后不可原地修改。** 修改代码、镜像、关键配置或目标，产生新候选并重新判断授权。
- **状态更新带预期状态和版本号。** 使用条件更新及唯一约束控制竞争，不依赖进程内判断。
- **批准与入队原子提交。** 审批决定、唯一操作记录和入队通过同一事务完成；实际执行前再次核对权限、有效期和撤销情况。
- **长任务使用短事务。** 模型调用、构建、人工等待期间释放连接和数据库锁。
- **队列完成不等于业务成功。** 发布是否成功取决于正式操作记录及实际运行验证。
- **检查点不替代审批。** 恢复时重新核对任务版本、执行权、预算、规则与有效授权。
- **敏感数据采用引用和脱敏。** 普通日志、工具结果和 checkpoint 不保存基础设施凭证；受限原始源码与证据独立控制访问。
- **大产物保存在产物存储。** 数据库保存摘要和引用，不保存完整镜像或持续追加的原始日志。

pg-boss 支持通过事务适配器将入队与应用写入放在同一事务内，P0 必须验证选定 Drizzle 组合的提交与回滚行为。[pg-boss 事务适配器](https://pgboss.io/api/adapters)

领域提交、图检查点和外部操作之间仍存在故障窗口。恢复逻辑需要核对这些记录，不能假定一次框架保存覆盖整个业务动作。

## 6. 并发由资源和执行权控制，MVP 默认串行。

| 层次 | MVP 策略 |
|---|---|
| API 请求 | 支持异步并发；限制请求量、负载大小和数据库连接 |
| 业务工作流 | 全局同时执行一个，其余排队或暂停 |
| Agent 角色 | 同一任务内串行交接，单 run 只有一个有效执行者 |
| 工具调用 | 按工具配置限额；独立只读检查可以受限并发 |
| 修复工作区 | 单写者，避免两个执行者同时修改 |
| Runner | 显式配置虚拟机、CPU、内存、磁盘和超时上限 |
| 应用环境 | 发布、重启、回滚共享同一变更协调机制 |
| 健康检查与核对 | 轻量、独立限额，不占用模型执行槽位 |

pg-boss 只负责**调度与唤醒**；领域服务定义外层阶段状态机；LangGraph 执行角色循环并保存上下文。首期不再用队列的流程功能定义第二套业务编排。

需要明确处理六种情况：

1. **等待审批：** 保存必要状态和产物后释放执行槽位；批准后重新入队。
2. **父子任务：** 运维创建代码修复任务后释放槽位，避免父任务占槽等待子任务。
3. **Worker 失去执行权：** 旧执行代次不能继续提交正式结果或调用新工具。
4. **外部操作超时：** 记录为结果未知，先核对实际状态；相关环境暂停新的冲突变更。
5. **重复投递：** 使用同一个逻辑操作 ID、幂等键和执行记录核对，不能直接重复部署或重启。
6. **取消：** 停止新增工具调用并清理执行环境；已经发出的外部操作需要继续核对，不能直接宣称已撤回。

数据库连接池按 API、Worker、队列和 checkpointer 统一核算总额度。整个 Agent handler 不包在一个数据库事务中。

pg-boss 提供心跳和取消信号，但取消信号不能强制停止忽略它的执行逻辑，因此平台和 Runner 仍需落实停止与超时控制。[pg-boss Worker 说明](https://pgboss.io/api/workers)

## P0 先验证技术组合和高风险接口，形成实施基线。

重点涉及 M02、M05、M06、M08、M09、M10、M13。

| 任务 | 工作 | 依赖与产出 |
|---|---|---|
| P0.1 | 定义任务、run、候选、审批、操作与规则关系 | 先形成领域契约、状态转换及完成条件 |
| P0.2 | 验证 TS、模型、LangGraph、checkpointer 和 MCP 客户端组合 | 依赖初版契约，产出兼容矩阵 |
| P0.3 | 验证 Drizzle、pg-boss 的事务、重试、取消和崩溃恢复 | 产出数据库及调度决策 |
| P0.4 | 验证虚拟机创建、执行、资源限制、重置和网络隔离 | 产出 Runner 契约 |
| P0.5 | 验证 Komodo 发布，以及 Whiskers MCP 原生确认流程 | 产出适配器契约与真实结果 |
| P0.6 | 准备标准应用、缺陷、正常反例和运维故障 | 产出首批评测材料 |
| P0.7 | 汇总版本、许可证、边界和剩余风险 | 依赖上述结果，冻结实施基线 |

本阶段特别验证：

- MCP 连接中断后能通过任务 ID 继续查询。
- 入队事务回滚时，业务记录与任务同时回滚。
- 任务已接收但尚无 checkpoint 时崩溃，仍能识别并恢复。
- 个人模式中，人类身份可以按下游规则确认服务身份发起的操作。
- Whiskers 批准后重试的参数必须保持一致，修改或过期不能复用批准。

Whiskers 当前文档将直接 MCP 确认描述为批准后重试，且权限没有逐服务器或租户范围，因此首期继续限定单一运维信任域。[Whiskers 治理流程](https://github.com/LupusMalusDeviant/Whiskers/blob/v1.0.1/docs/governance.md)、[权限边界](https://github.com/LupusMalusDeviant/Whiskers/blob/v1.0.1/docs/v1/PRODUCT_CONTRACT.md)

**验收标准：**

- 一个真实外部 MCP 客户端完成认证和调用。
- 模型能够根据工具结果继续执行、调整或停止。
- 一次测试镜像通过 Komodo 发布，并核对实际版本。
- 一次真实 MCP 写操作完成未批准阻断、人工批准、执行和验证。
- 虚拟机可清理至干净状态，任务环境无法读取控制面凭证。
- 数据库事务与恢复验证通过，形成版本清单和架构决策记录。

适配器无法满足契约时，可以调整或替换实现；Agent 运维、MCP 和人工闸门继续保留。

## P1 建立可授权、可恢复的真实任务底座。

依赖 P0，主要完成 M01、M02、M05、M06、M07、M08、M13，并交付最小 M12。

| 任务 | 工作 | 主要依赖 |
|---|---|---|
| P1.1 | 身份、项目、应用、环境及下游资源登记 | P0 契约 |
| P1.2 | 领域表、迁移、状态转换、事件和操作记录 | P1.1 |
| P1.3 | pg-boss、事务入队、执行权、取消和检查点恢复 | P1.2 |
| P1.4 | 工具网关、Runner、固定快照和真实扫描器 | P1.1—P1.3 |
| P1.5 | API、外部 MCP、任务列表与详情 | 前述能力及共享契约 |

本阶段对外提供规则查询、预审、任务发起、状态查询和取消。长任务返回任务标识，门户和 MCP 共用领域服务。

工具返回统一区分成功、业务失败、基础设施失败、等待批准和结果未知。正式扫描缺失、超时或不支持时记录覆盖限制。

**验收标准：**

- 固定 Git 版本能够完成真实扫描并保存脱敏证据。
- API 或 Worker 重启后，任务仍可查询并按规则恢复。
- 重复请求不会创建重复逻辑任务或操作。
- 两个执行者竞争同一个 run 时，只有一个获得有效执行权。
- 错误项目、越权目标、越界文件和非法工具参数在执行前被拒绝。
- 取消后不启动新工具，执行环境可清理。
- 门户与 MCP 状态一致。
- 平台事件可以关联到任务、run、工具调用及产物。

P1 可以尚无完整 Agent 推理，实际执行与持久化基础必须成立。

## P2 跑通 Agent 审计、修复、复验和发布。

依赖 P1，重点完成 M03、审计/修复/复验角色、M09 和交付页面。

| 任务 | 工作 | 主要依赖 |
|---|---|---|
| P2.1 | Harness：目标、工具循环、上下文、预算、无进展与转人工 | P1 |
| P2.2 | 审计、业务化清单、修复及角色交接 | P2.1 |
| P2.3 | 干净环境复验、基线、回归检查和最终镜像扫描 | P2.2 |
| P2.4 | 冻结候选、人工确认、有效期和变更失效 | P2.3 |
| P2.5 | Komodo 发布、实际版本及健康验证 | P2.4 |
| P2.6 | 复验失败返修、预算耗尽、取消和异常恢复 | 贯穿上述步骤 |

Agent 允许选择模板修复或受限代码修改。审计区分确认、疑似和未覆盖事项；业务化清单保留证据、影响、修复方式和升级原因。

复验读取受保护的基线和测试。修复 Agent 无权关闭扫描、降低发布要求或自行宣布正式通过。

必要页面包括任务进度、发现、代码差异、复验结果、冻结候选和人工确认。

**验收标准：**

- 外部编码助手通过 MCP 启动完整交付任务。
- 至少两类可客观验证的问题完成发现、修改和复验。
- 不同工具结果能够引出不同调查路径；失败后能调整方案或停止。
- 修复产生真实代码差异、固定快照和可导出补丁。
- 回归样例被受保护检查识别并阻止发布。
- 未经人确认不能发布；本人确认明确留痕。
- 审批后替换镜像、代码或关键配置，旧授权失效。
- 实际运行镜像与候选一致，健康和访问保护检查通过。
- 下游执行后响应丢失时，进入核对流程，不盲目再次发布。

**P2 交付第一条可演示的完整开发路径。**

## P3 完成真实 Agent 运维和关联修复。

依赖 P1，使用 P2 已发布的应用验收，重点完成运维角色及 M10。

| 任务 | 工作 | 主要依赖 |
|---|---|---|
| P3.1 | 封装 Whiskers MCP 观察、确认与执行契约 | P0 验证、P1 网关 |
| P3.2 | 运维 Agent：证据、假设、调查、计划与停止条件 | P2 Harness、P3.1 |

| P3.4 | 健康异常触发、事件去重、冷却与次数限制 | 前述能力 |
| P3.5 | 代码问题进入关联修复任务 | P2、P3.2 |

职责沿用 v6：

- Komodo 管理发布配置和版本恢复。
- Whiskers MCP 提供观察与受控重启。
- 平台管理身份、项目范围、操作协调、授权和证据关联。
- 平台与下游原生批准状态关联，未满足条件时继续暂停。

**验收标准：**

- 停止应用后，Agent 收集实际证据，获批后重启并验证恢复。
- 新版本故障时，Agent 能调查最近发布，并申请恢复指定已发布版本。
- 未批准、批准过期、权限撤销或目标变化时，执行被阻断。
- 持续故障不会导致无限重启，能够停止或升级人工。
- 发布与重启竞争时，不发生冲突变更。
- 结果未知期间，相关应用环境不接收新的冲突操作。
- 代码缺陷创建关联修复任务，沿用正式交付流程。
- 门户与外部 MCP 都能发起诊断并查询真实结果。
- 平台记录与下游批准、执行和审计 ID 可以串联。

**P3 完成开发与运维两条闭环。**

## P4 完成 Skill、规则和 Runbook 的验证发布及后续复用。

依赖 P2、P3 的真实案例，重点完成规则提炼角色和 M11。

| 任务 | 工作 | 主要依赖 |
|---|---|---|
| P4.1 | 规则包元数据、导入、版本、审核和回滚 | P1 身份与产物 |
| P4.2 | 从真实任务提取案例、查重、判断适用范围 | P2、P3 |
| P4.3 | 生成代码规则、Runbook 和正反样例 | P4.1、P4.2 |
| P4.4 | 隔离验证、人审、正式发布 | P4.3 |
| P4.5 | 在后续任务中检索、执行并验证复用 | P4.4 |

规则包支持 Skill 指导、参考资料、设计资源、声明式检查及验证样例。首期代码规则限定一种检查器格式，Runbook 限定工具目录中的已知动作。

设计规范提供一个通用示例：文字指导供 Agent 使用，可自动检查的条目声明为检查规则，其余明确标为人工检查。

上传内容不执行任意插件脚本，也不直接成为控制面动态执行代码。规则检索先使用元数据、关系和全文检索。

**验收标准：**

- 至少一条代码规则完成生成、正反样例验证、人审发布。
- 第二个同类项目由正式检查器命中新规则。
- 正常反例通过，规则没有只记住原文件或变量名。
- 至少一条 Runbook 在后续运维任务中被正确使用。
- Runbook 使用当前权限、审批、次数限制和停止条件。
- 导入的 Skill 无法修改正式基线、扩大权限或发布自身。
- 回滚后新任务使用正确版本，历史任务保留原规则和证据。
- 任务启动固定规则版本；撤销或强制更新按策略使相关授权失效。

**P4 完成时，三条功能闭环全部存在，才算功能完整的 MVP。**

## P5 验证可靠性并形成可复现的开源交付。

依赖所有前置阶段，完成集成回归、故障注入、备份恢复和发布材料。

| 验证类别 | 必须覆盖 |
|---|---|
| 模型与 Agent | 非法结构、错误参数、重复动作、无进展、模型不可用、预算耗尽 |
| 数据与调度 | 原子入队、重复投递、状态竞争、Worker 崩溃、检查点不一致 |
| 人工介入 | 暂停恢复、重复批准、过期、撤销、本人确认及 Agent 伪造批准 |
| 外部执行 | 已执行但响应丢失、结果未知、下游不可用及恢复后核对 |
| 并发 | 重复恢复、失效执行者、发布与重启竞争、父子任务等待 |
| 隔离与输入 | 越界路径、凭证读取、跨任务残留、仓库/日志/Skill 误导指令 |
| 数据恢复 | 数据库、产物、规则和配置备份后的关联与状态恢复 |
| 安装与升级 | 干净安装、版本迁移、依赖锁定、文档重建环境 |

故障恢复后，先核对未完成操作，再恢复执行；离线回放使用隔离环境或记录的工具结果。

**发布验收：**

- 三条闭环在干净参考环境中可复现。
- 开发与运维正向路径各完成至少三次独立运行。
- 权限、版本绑定、原子入队、执行权、去重和取消的确定性用例全部通过。
- 结果不确定时保持明确状态，不能报告成功。
- 完成一次实际备份恢复，检查数据库与产物引用一致。
- 治理服务不可用时，目标应用不会自动变为匿名开放。
- 依据文档可以重新安装并运行示例。
- 依赖、镜像、模型配置、规则及许可证清单齐备。
- 提供真实质量、耗时、成本和资源报告，注明支持范围。

开源核心沿用 Apache-2.0 建议；权限、审批、审计、恢复和评测属于核心功能。第三方组件和规则按各自许可证处理。

## 8. 评测从 P0 建设，随着闭环逐阶段扩充。

首批准备约 **20—30 个可重复案例**，包含：

- 可修复的代码、依赖或配置问题。
- 正常代码与易误判反例。
- 修复引入回归。
- 需要人工介入或超出支持范围的任务。
- 可恢复及持续性的运维故障。
- 授权、恶意输入、重复执行与崩溃恢复场景。

保留一部分案例作为不参与提示词调优的验证集。规则生成样例之外，还需要独立反例和后续项目验证。

评测检查实际代码、报告、运行状态和操作记录，允许 Agent 采用不同工具路径。对简单任务保留确定性流程作为对照。

| 目标 | 观察指标 |
|---|---|
| 审计质量 | 检出、误报、覆盖限制 |
| 修复质量 | 实际修复、回归、返修与人工介入 |
| Agent 行为 | 无效调用、重复动作、无进展停止和预算 |
| 运维质量 | 恢复时间、错误处置、重复操作和升级处理 |
| 系统可靠性 | 队列等待、恢复结果、结果未知与核对耗时 |
| 维护成本 | 模型成本、Runner 利用率、数据库连接等待 |
| 沉淀价值 | 后续命中、误判、Runbook 复用和规则回滚 |
