# P2-E-C3-B · 正式发布队列认领与执行权

基于 [Registry 导入 #45](https://github.com/MaLaNg116/itervane/pull/45)、[Registry 来源绑定 #46](https://github.com/MaLaNg116/itervane/pull/46) 和 [正式人工审批 #41](https://github.com/MaLaNg116/itervane/pull/41)。 [C3 分批计划](p2-e-formal-release-execution.md#c3-执行权分批)

## 认领与恢复

1. 正式消费者以唤醒消息中的 `operationId` 重建操作。按全局执行槽、当前任务、目标环境与操作加锁。核对 pg-boss 唤醒身份、最新冻结候选、任务代次、正式复验、批准人的当前授权版本、请求人的项目授权、目标版本和 Worker 安装来源。锁定后再读 PostgreSQL 时间确认候选与租约有效。
2. 认领事务分配全局 fence、记录发布专用运行阶段和绑定操作、持有既有环境排他索引，并原子结算本次唤醒。重复或过期唤醒有明确结算结果。信号、数据库故障与排队竞争均以持久化事实为准。
3. 心跳和每次可信步骤通过同一执行槽、任务及操作核对 fence。完成后的旧 Worker 不能继续行动。源码队列识别正式发布运行阶段。执行权过期后，如果尚未保存任何外部写入意图，则恢复同一操作的正式唤醒。C3-C 接入步骤记录后，已保存外部写入意图的操作进入待核对状态。
4. 现有派发前撤销与用户取消继续使用当前权限和版本。认领后发生取消时，Worker 通过取消信号停止继续写入并记录事件。C3-C 负责确立下游已发生的事实。发布遇到未知结果时，环境占用与原始操作关联保留。

## 验收

- 真实 PostgreSQL 对照同一操作的并发认领、普通源码任务占槽、环境持有、重复与未经登记的唤醒。
- 获得数据库锁后阻断审批过期、撤销重授、请求人越权、目标变化、错误的 Registry 来源与已替换证据。验证拒绝的任务事件和状态一致。
- 验证过期 fence 无法接着使用，正式操作恢复到专用队列，取消和运行迁移可追溯，普通队列行为通过回归。
- 采用可信执行探针验证认领和交还执行权。C3-C 将已核对 Registry 适配器接到正式 Worker 的步骤账本，C4 接续 Komodo 和独立运行核对。
