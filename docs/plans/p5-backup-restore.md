# P5-A · 控制面备份与恢复

依赖三个已实现闭环的领域数据与原生交付档案。本批启用维护者执行的冷备流程，并在独立的 PostgreSQL 17 目标与新文件目录上确认恢复结果。 [实施计划 v2 的 P5 出口](../implementation-plan-v2-ts-postgresql.md#p5-验证可靠性并形成可复现的开源交付) · [#159](https://github.com/MaLaNg116/itervane/pull/159)

1. 使用 PostgreSQL 17 客户端导出控制面、Drizzle 迁移、pg-boss 和 LangGraph 四个 schema。维护者先停止 API 和所有消费者，保留待处理任务及历史。以确定性清单记录数据库留存表、归档、维护者选定的配置和各文件摘要。留存 OCI 档案以复验证据和发布候选引用为准，恢复时仍使用 Runner 的内容寻址命名。
2. 恢复只接收维护者可信的备份，预检文件摘要、目标空库和目标目录。使用 PostgreSQL 单事务恢复，重新核对数据库清单与 OCI 引用，在新目录写入复原回执。由环境管理员重新赋予运行角色并从受管配置注入凭证。
3. 使用两个独立的 PostgreSQL 17 实例实做导出和恢复，核对已发布的设计规则、旧任务版本、任务事件、排队与检查点、OCI 字节和配置。验证损坏备份、缺失档案及重复恢复会被拒绝。恢复后的运行账号仍使用原权限服务读取，排队执行仅在人工核对下游后启动。
4. 用托管 KVM 的真实已验证镜像、发布和运维回执再做整批演练，将恢复结果放入 P5 发布证据。目标应用数据与外部组件的数据各由所用服务独立备份，控制面恢复期间保持独立受保护入口。队列中的旧批准和外部未确认动作需单独核对实际状态，按现有取消、失效和对账路径处置。

导出命令使用维护者提供的 libpq 环境配置，备份包留在私有存储。发布证据仅保留版本、计数、摘要和各项验证结果。 [PostgreSQL 17 导出](https://www.postgresql.org/docs/17/app-pgdump.html) · [PostgreSQL 17 恢复](https://www.postgresql.org/docs/17/app-pgrestore.html)
