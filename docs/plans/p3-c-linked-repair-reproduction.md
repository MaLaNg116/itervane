# P3-C3-C3 · 复现应用故障并验证关联修复

基于 #126 的确认、固定源码和正式发布闸门。使用标准 Web 应用验证一条完整链路，从受保护的健康异常与日志进入诊断，再经隔离复现、受限修复、独立复验和人工发布，最后核对新实例的健康结果。 [阶段计划](p3-c-operations-incidents.md#c3-c-从诊断进入关联修复) · [源码核验](p3-c-linked-repair-admission.md)

| 批次 | 实施与验收 |
| --- | --- |
| C3-C3a 隔离复现 | 为标准应用增设登记的连续健康检查。沿用现有受保护的运行探针、工件、构建环境和一次性 VM。固定检查类型、请求次数和目标，记录原始源码的实际响应、同版本证据与 VM 清理。授权失效、证据不符、入口不可用或故障未出现时分别结算。 |
| C3-C3b 受限修复与复验 | 复现证据与已冻结的诊断、源和任务绑定。正式审计读取可信检查结论并移交关联代码问题，修复只读取和修改标准应用策略明确的业务文件范围。保留原始内容摘要和可导出补丁，复验从新的 VM 同时执行标准基线、同一健康用例、扫描和新增问题比较。 |
| C3-C3c 原生联验 | 在实际可访问的受保护应用上验证一个只在连续健康请求下出现的代码缺陷。断言发布后新建事件、诊断回读、人工接受、原版复现、实际代码变化、新版复验和重新审批。通过 Komodo 双版本证明、Whiskers 脱敏日志和独立入口核对恢复，保存可重放的报告。 |

用维护者封存的标准探针执行固定次数的本机健康请求，核对 HTTP 状态、响应结构和已发布版本。模型在诊断与修复中使用结构化证据。复现配置和目标从安装策略与领域记录解析。现有基线继续独立执行，复现时的原版失败单独入库，复验必须在同一条件下得到实测通过。 [标准探针](../../fixtures/runner/standard-web-baseline.mjs)

C3-C3a 将第二次 `/health` 请求放在原有首次健康检查之后。保持标准基线五项记录，额外记录续测结果。只有同版本、结构合格的 HTTP 503 认作应用故障，超时、连接失败和内容不符保留各自原因。由正式关联任务引用的健康样本开启复现。冻结输入绑定提案、诊断、发布证明和样本摘要，继续使用已有复验账本、调用租约与 VM 清理回执。原版续测通过时进入人工核对，正式发布等待 C3-C3b 对已修复内容完成同条件复验。

真库验收覆盖同一关联的复现幂等、授权撤销、运行接管、过期回执及不同实例。原生验收明确真实 KVM、PostgreSQL、Komodo、Whiskers、身份入口及实际模型协议范围。C3-D 接续双语事件和关联任务界面、外部 MCP 与停止操作。
