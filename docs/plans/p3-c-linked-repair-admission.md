# P3-C3-C2 · 人工确认关联修复与固定源码

基于 #125 的不可变提案。交付任务沿用现有 PostgreSQL、pg-boss、执行槽、隔离 Runner 和正式发布路径。 [阶段计划](p3-c-operations-incidents.md#c3-c-从诊断进入关联修复)

1. 门户所有者提交提案指纹和选定的不可变提交。事务内核对本人当前授权、提案者授权、诊断证据、有效期和环境占用。新任务、接受事件、首次唤醒和一次确认的证据同事务写入。重复提交返回同一任务，改变已确认的指纹、源码或语言时返回冲突。确认记录保存批准人、项目授权代次和是否本人确认。
2. 交付任务沿用 `audit` 入口和现有模型约束。首次取源核对登记来源和固定提交。若发布基于该提交的原始快照，核对合格回执的 Git 快照摘要。若已发布候选包含补丁，确认者给出同一仓库里固化该补丁的提交。可信 VM 从该提交重算文件清单，使用提案中的原始源码引用和摘要重算已发布候选清单，匹配后才把回执交给正式审计。文件内容和元数据留在隔离执行侧，证据摘要绑定本次请求与租约。
3. 任务领取和接管核对确认人的当前授权代次，复用已有取消、重试和检查点。发布候选以提案绑定的环境为准，批准前复查其当前发布和登记。候选仍需要完整扫描、独立复验和单独的本人确认。

验收覆盖并发确认、错误指纹、外部 MCP 身份越权、授权撤销与重授、资格过期、单次事务失败、任务接管及目标更换。在隔离 Runner 核对原始提交、正确固化的补丁和文件不同的替代提交。继续保留审计与复验的完全覆盖要求。门户交互与外部 MCP 读取由 C3-D 交付。
