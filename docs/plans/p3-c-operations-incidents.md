# P3-C3 · 健康事件与关联修复

接续 P3 的正式诊断、受控重启和指定版本恢复，落实实施计划 P3.4 与 P3.5。故障由实际发布和独立读取支撑。运维 Agent 继续给出诊断和建议，变更沿用门户审批及执行账本。 [蓝图 v6](../blueprint-v6.md) · [实施计划](../implementation-plan-v2-ts-postgresql.md) · [处置计划](p3-c-operations-proposals.md)

| 批次 | 工作与验收 |
| --- | --- |
| C3-A1 健康事件账本 | 绑定项目、环境、部署登记、最近一次已核验的发布或恢复实例。持久化受信健康样本及事件记账，使用数据库时间、原子去重和当前实例校验。真库覆盖重复、并发、陈旧实例、错误作用域和待核对处置。 |
| C3-A2 原生探针 | 在固定安装范围内独立读取应用健康，区分应用异常、探针不可用和目标变化。探针查询已登记的受保护入口和原生实例。以真实发布、故障、恢复和身份服务不可用验证事件含义。 |
| C3-B 事件去重与诊断准入 | 按当前实例聚合健康异常，使用冷却、限次、去重和持久化唤醒。登记的诊断服务身份按当前项目范围创建诊断，沿用真库队列和全局执行槽。持续故障到达预算后交给人工。验证同时到期、重复领用、重启、过期权限和已占用环境。 |
| C3-C 关联代码修复 | 由已核验诊断产生可确认的修复入口，连接事件、诊断、不可变源码及既有交付任务。真库验证重复确认、权限撤销、源替换与审计链。实际缺陷从事件进入正常的审计、修复、复验和新版本发布。 |
| C3-D 双语读面与联验 | 门户在现有应用与任务页呈现事件及相关诊断、处置和修复。与外部 MCP 共用权限和证据投影，保持中英文、GSAP 和减少动效偏好。用同一受保护应用验证触发、人工停止、恢复与后续修复，并保存可复跑的导读。 |

C3-A 先建立健康样本和事件账本。健康样本关联固定来源、时间与实例，审批、写指令及原生凭证分别由现有处置流程保管。历史样本随原发布保留。资格未知时保留状态和已知证据，等真实读取确认后再恢复调度。

调度资格依赖可确认的健康异常、当前登记和当前授权。周期探针与临时不可用都由可信进程和数据库定界。相同事件创建诊断时复用已有任务，持续异常使用有界预算。后续恢复和修复挂回事件，供 P4 提炼验证规则和 Runbook。正式入口依赖前置原生装机和本批联验。

C3-A2 由单独启动的只读 Worker 按固定安装取样。读取前后校验当前登记、发布回执和环境占用。Komodo Read 身份核对当前容器。只有同一容器明确退出，或受保护入口返回同一版本的合格异常响应，才记录应用异常。身份不可用、入口失效或目标变化记录探针不可用，保留当前事件。原生场景验证运行正常、停止、重启恢复、应用返回 503 和身份服务中断。配置、周期和凭证独立于正式诊断与处置 Worker。

## C3-B 健康异常到正式诊断

| 批次 | 内容 | 验收 |
| --- | --- | --- |
| C3-B1 持久化准入 | 安装者登记单环境的内部诊断主体、项目授权代次、入口登记、模型和有效期。当前可信异常、诊断任务、触发证据关联和 pg-boss 入队在同一事务核对。正式 Worker 重查授权、监控登记和异常实例，沿用全局执行槽。 | PostgreSQL 验证重复轮询、入队回滚、恢复后窗口、配置替换、权限撤销和已占用环境。 |
| C3-B2 轮询与原生联验 | 可选把准入接到 Health Worker。重启后从数据库读取异常和前一次诊断，复用现有诊断 Worker 的 MCP 观察与模型。 | 在受保护应用的真实异常上核对诊断入队、领取和回执。探针失联、恢复、资格过期与预算耗尽使用确定性负例。 |

每个异常事件最多接收三次自动诊断。同一环境任两次成功准入至少间隔两分钟。重试须看到比上次准入更新、最多六分钟的异常样本，且前一次诊断已经成功结束。取消、诊断转人工或耗尽预算时，保留停止原因。未完成任务和冲突操作会延后下一次准入。已关闭事件、末次探针未知和登记失效都暂停新准入。

监控主体使用内部发行方及同项目授权，凭证只由已登记的诊断 Worker 持有。任务的接收记录可追到触发样本和监控登记，处置依然由门户本人确认。用户停止与双语事件查询在 C3-D 接入。

### C3-B2 装机与原生验收

Health Worker 通过可选登记 ID 接入 C3-B1。每次完成健康采样事务后，从数据库重新读取当前环境与最新证据，调度事务沿用原诊断队列。监控撤销、过期和探针失联保留健康记录，由常规诊断 Worker 使用独立身份与全局槽处理已有任务。

原生用例使用同一已发布容器的实际退出与恢复。预期停止样本只产生一笔正式诊断。重新安装 Health Worker 后重复采样，返回同一任务。实际诊断 Worker 消费队列并使用真实 Whiskers 及 Anthropic 协议夹具产出回执。核对任务、样本、模型、发布、作用域和中英文 HTTP/MCP 查询。撤销登记后继续记录真实 503、身份服务中断和恢复，原来的恢复授权负例继续验收。

## C3-C 从诊断进入关联修复

| 批次 | 内容 | 验收 |
| --- | --- | --- |
| C3-C1 修复提案 | 重读结算成功、证据支持 `investigate_code` 的正式诊断。保存诊断摘要、当前发布或恢复、发布证明、仓库固定版本和快照证明。监控触发的提案引用原事件和触发样本。 | PostgreSQL 核对跨项目拒绝、错误建议、已替换的发布、仓库来源不符、过期及同诊断的并发创建。对照已发布镜像核验原始和修复后快照。 |
| C3-C2 人工确认与正式交付任务 | 门户所有者按提案指纹确认，重新检查当前实例、身份与授权。创建标准交付任务、关联及 pg-boss 唤醒，并按诊断提案去重。首次 Runner 读取核对固定源码，后续执行和发布继续核对授权和目标。 | PostgreSQL 核对重复确认、授权失效、来源漂移、入队回滚、执行槽接管和发布目标变化。VM 拒绝源码内容与冻结基准不一致的确认。 |
| C3-C3 代码变更与发布回执 | 为实际出现的故障建立受管的复现证据，交给审计、受限修复与独立复验。保留修复差异、针对性复验、人工发布确认及实际健康结果。 | 托管 KVM 从同一受保护实例的健康异常和日志出发，核对关联任务、修复差异、独立复验、新批准版本及运行恢复。加入来源替换和复验失败的负例。 |

运行实例的已发布证明是提案基准。仓库原始快照和实际发布的修复后快照分别保存。如果运行实例包含尚未进入仓库的补丁，确认者可提供同一登记仓库里已应用该补丁的固定提交。由合格 Runner 用该提交的实际文件清单重算原候选的内容证明，再开放源码审计和修复。快照核对使用已发布证明和可信 VM 回执。模型、客户端或新提交自身声明的摘要都没有验收效力。

诊断留在只读任务。提案引用发布时的应用、环境、授权范围和观察证据，并沿用登记策略的确认期限。门户确认是接收关联任务的授权，后续发布继续有独立候选、复验、审批和外部核对。无来源事件的手动诊断仍可提出关联修复，保留它的实际触发渠道。C3-D 负责门户呈现、外部 MCP 的授权读取和停止诊断。
