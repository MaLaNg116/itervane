# P2-E-B · 正式候选的人工决定与发布队列

基于[候选冻结 #40](https://github.com/MaLaNg116/itervane/pull/40)，沿用 [P2-B 人工决定](p2-b-release-candidate.md) 和 [P2-C 事务与结果核对](p2-c-release-reconciliation.md) 的领域约束。 [P2-E 实施计划](p2-e-formal-release.md) · [蓝图 v6](../blueprint-v6.md)

| 批次 | 交付 | 验收 |
| --- | --- | --- |
| B1 候选确认与正式队列 | 用现有决定和操作表记录同一候选的确认、拒绝与派发前撤销。复用当前 OIDC client、工作区所有者和数据库授权版本核验。确认后在同一事务保存决定、任务状态、操作与正式队列唤醒。 | 并发与重放只有一个决定和操作。审批窗口内锁住同一代次、实际归档证据、目标版本和权限。过期、换代、改配置、撤权或错误登录来源按原资格拒绝。事件或入队失败整体回滚。 |
| B2 双语审批面板与外部读取 | 任务详情显示固定候选、运行目标、镜像指纹、风险、期限与决定历史，维护者通过人用门户确认。外部 MCP 查询相同的已授权投影。 | 中英文、键盘与减少动效、取消、改版前后和只读角色通过浏览器验收。MCP scope 和项目成员关系按每次查询重新核对。 |

审批引用候选 ID、完整指纹、预期决定版本和幂等键。冻结请求本身只选择已有环境。个人模式的本人确认在现有 `selfConfirmed` 字段留痕。服务端在获得任务和环境锁后读取 PostgreSQL 时间，核对有权确认的授权版本以及最新证据，再提交事务。已确认的旧候选在目标版本或任务代次变化后失去派发资格。

正式队列有自己的受控消费者入口，后续 E-C 使用同一个全局执行权和环境锁。队列消息只携带操作 ID，派发的目标、镜像和配置从账本和登记记录重建。进入派发前可撤销并结算排队操作。开始派发后的状态核对由 E-C 处理，保持对端副作用的不确定性。

## B2 落地顺序

1. 任务详情使用同一事务下的任务代次、版本、候选和当前授权。登记目标只投影项目内的应用与环境名称、标识和登记版本。目标选择仅在当前复验有归档核对证明且当前主体可准备候选时出现，冻结命令仍独立核对目标策略和完整证据。已有候选按数据库时间、任务代次、目标版本及批准人授权即时计算状态。
2. 外部 MCP 增加 `get_release_candidate`。它复用现有候选 HTTP 查询服务，每次执行核对 `itervane:read` 和当前项目成员关系，返回同一候选指纹、证据、状态与决定历史。蓝图中的 MCP 发布申请后续单独接入现有冻结命令，携带明确环境和任务版本。人工决定继续使用人用门户客户端的已核验身份和工作区所有者授权。
3. 双语任务详情允许准备候选，查看冻结的目标、期限、镜像风险与指纹，以及决定历史。确认、拒绝与派发前撤销均通过可用键盘操作的对话框发起，记录打开时的候选指纹、预期决定版本及同次请求幂等键。查询发现权限、候选状态或指纹变化时清掉待确认的操作。详情展开沿用 GSAP 和减少动效设置。
4. 以真实 PostgreSQL 和 MCP 客户端验证空候选、可读投影、改版、撤权与权限拒绝。在真实 Chrome 和 Keycloak 会话中验证中英文、用键盘核对指纹及取消、并发更新、批准和撤销结果，分别记录浏览器覆盖及真实隔离回执来源。审批成功展示已入队，Komodo 执行和真实上线验证由 E-C 负责。
