# P2-E-C · 制品导入与受控 Komodo 派发

基于[正式队列 #41](https://github.com/MaLaNg116/itervane/pull/41)、[人工审批 #42](https://github.com/MaLaNg116/itervane/pull/42)和[外部 MCP 发布申请 #43](https://github.com/MaLaNg116/itervane/pull/43)。退出判据沿用 [P2-E 总计划](p2-e-formal-release.md) 和 [v6 蓝图](../blueprint-v6.md)。Komodo v2.3.4 的固定测试组合与权限契约见 [P0 原生验收](../reviews/p0-komodo-native-delivery.md)。

## 分批开发与验证

| 批次 | 交付 | 验收 |
| --- | --- | --- |
| C1 · 受控读取已留存 OCI | Runner 宿主控制器通过现有受保护的本地 socket 按固定描述传输归档。发布 Worker 在私有暂存区独立核对实际字节数与 SHA-256。 | 一次性 KVM 环境产生的归档可在已确认清理后读取，归档内容与同代回执一致。拒绝未留存、路径或符号链接变换、不同 Runner、改内容、截断、超限和撤销期间的传输，失败后移除本次暂存。 |
| C2 · 固定镜像导入 | 发布适配器使用安装维护者登记的受控 Registry，校验归档后以保留 digest 的方式导入，按摘要读取 Registry 中的实际 manifest 并核对配置 digest。 | 临时真实 Registry 接收同一归档。原始 manifest 响应字节、响应 digest、配置标识和登记仓库对应。错仓库、标签漂移、权限错误及失败结果无法产生发布证明。 |
| C3 · 正式队列认领与恢复 | 专用消费者复用全局执行权、代次和目标环境锁。根据操作 ID 重建批准条件，持久化每一步派发事实及恢复状态。 | 真实 PostgreSQL 验证重复唤醒、竞争、审批过期、撤权、配置变化、取消、进程退出及移交。待核对的操作保留环境占用和事件。 |
| C4 · 有界 Komodo 执行 | 以仅能访问登记目标的服务端账号核对服务器、部署和配置。按已证明的镜像摘要写入配置并派发，记录原生更新证据。 | 真实 Komodo 验收目标范围限制、已登记配置与执行结果对应、网络中断后的只读核对。分阶段连接 Registry、正式 Worker 和实际部署适配器。 |

## 制品与操作绑定

- C1 复用现有 socket 文件与 Linux peer UID 检查、已留存归档描述、按摘要生成的文件名，以及私有目录内的文件权限和大小约束。请求只有摘要和长度，服务端只读取规则允许的已留存文件。开始传输前核对 Runner 版本与 Worker 执行权，使用固定长度与有界超时的流。Worker 重新计算完整摘要并读取传输结束标记后，才把私有暂存交给下一步。C1 由独立的可信验证入口调用。
- C2 只对通过 C1 字节核验且仍在授权中的操作导入。导入工具接收服务端固定参数、私有暂存及受限凭证。Registry 的仓库名来自登记，Komodo 引用来自独立回读确认的 `repository@sha256:…`。把同一 digest 已存在的状态作为可查询结果。
- C3 的唤醒只持有操作 ID。按全局执行槽、任务、环境和操作的次序锁定并再次核对当前代次、冻结指纹、决定版本、授权、有效期及登记目标版本。Worker 在每次外部写入前持久化对应的步骤意图并核对 fence。关闭或恢复 Worker 时，对已经记录意图的步骤先读后端实际状态。
- C4 将配置更新和实际部署分别绑定到同一候选和操作。已获得的下游更新 ID 用于查询完成结果。丢失回执时依据原生记录、操作归属与实际目标状态核对，保留证据不足的操作供人工处理。E-D 在真实运行目标上独立核对版本、配置、访问保护及健康，再结算任务。

外部助手可以申请发布并查询状态，维护者确认之后由正式 Worker 推进。测试使用公开或合成样例，用户项目依赖安装、构建和启动验证继续在合格的一次性 VM 中执行。放开部署 capability 需要走完 E-D 的真实出口。

## C2 参考实现

在与发布 Worker 相同的非 root 模式下，Skopeo 1.13.3 直接打开 `oci-archive:` 会尝试恢复 tar 记录的属主。先在私有目录内按固定文件名写入 OCI layout，重新验证归档 SHA-256、成员边界、manifest、配置和层，随后将目录交给 Skopeo。内容固定后使用 `--preserve-digests` 向 `repository@sha256:…` 导入。已在临时 Distribution 3.1.2 核对摘要写入以及 manifest 和配置原始字节。 [Skopeo copy](https://github.com/containers/skopeo/blob/main/docs/skopeo-copy.1.md) · [OCI Distribution 规格](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)

Registry 来源由安装维护者配置，镜像仓库名沿用任务目标登记。参考组合支持 HTTPS 与可选的 Basic 服务账号。本机匿名测试使用显式回环地址。在执行权核对后进行一次导入，随后独立读取固定 digest 下的 manifest 和 config，核对标头、原始字节与候选。拷贝进程异常时也先读 Registry 的可见状态。正式消费者接线时还需把实际 Registry 来源与已批准的目标版本绑定。

## C3 执行权分批

| 批次 | 交付 | 验收 |
| --- | --- | --- |
| C3-A Registry 来源绑定 | 安装登记将规范化的 Registry 来源与镜像仓库一同纳入目标版本摘要。导入器先核对 Worker 配置与批准目标的来源。 | 旧记录仍可核验指纹，补登来源或更换实际 Registry 会递增版本并使旧候选失效。同一来源的等价格式可重放。托管 OCI 从实际登记的来源导入。 |
| C3-B 发布队列认领 | 专用消费者在全局执行槽及环境锁内重读候选、授权版本、目标版本与数据库时间，为同一操作分配 fence。 | 真实 PostgreSQL 验证并发、过期、撤权和错配置拒绝，普通源码队列不会接手发布中任务。 |
| C3-C 发布步骤与恢复 | 保存归档交接及 Registry 导入的准备、确认和待核对记录，过期后用同一操作重建上下文。 | Worker 中断后先读实际 Registry 状态，确认同摘要后继续。环境锁在疑义消除前保留，既有决定和轨迹可查询。 |

历史登记保留原 JSON 形状及指纹。正式导入要求目标登记已包含来源且与 Worker 的地址一致，登记变更继续经过环境锁。候选通过现有目标版本和摘要绑定完整登记，门户和外部 MCP 继续使用有权限的目标展示字段。
