# P4-D2c · 第二个登记项目复用已发布代码规则

基于前一批已固定的检查和复验裁决，验收一条来自真实运行案例的规则能否作用于后续项目。 [#152](https://github.com/MaLaNg116/itervane/pull/152) · [TS + PostgreSQL 实施计划](../implementation-plan-v2-ts-postgresql.md)

1. 沿用托管的 503 → 200 关联修复案例、规则提炼、一次性 VM 正反样例和门户人工审核发布。记录实际发布的工作区规则版本、激活序号、审核摘要和验证回执。
2. 登记同一工作区的第二个项目和受信任的测试源码。固定一个存在相同问题的提交和一个正常反例，使用不同的文件或变量名。通过正式任务入口提交。核对两项任务引用的规则版本、来源项目与当前执行授权，并核对冻结后的源码、扫描覆盖和清理。
3. 正例应由真实 Semgrep 命中，审计 Agent 须读取正式扫描证据，再由现有流程进入人工核对。反例应通过规则检查与独立复验。用实际验证结果检查发布资格，保持目标、制品和审批绑定。
4. 在 PostgreSQL、OIDC 测试身份及托管 KVM 中核对每段证据。归档任务、版本、匹配项、目标清单、独立 VM 与清理摘要，注明模型适配器和下游服务的实测范围。Runbook 处置、权限撤销联动和 P5 重复运行分别按后续批次验收。
