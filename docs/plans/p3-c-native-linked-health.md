# P3-C3-C3c · 从受保护应用故障到新版本发布

接续 [#128](https://github.com/MaLaNg116/itervane/pull/128) 的修复和复验。用独立托管 KVM 场景从已发布的标准应用开始，验证真实健康事件如何经过受控诊断、关联修复与人工发布后收敛到新实例。 [阶段计划](p3-c-linked-repair-reproduction.md) · [受限修复计划](p3-c-linked-health-repair.md)

1. 部署固定合成应用到受保护入口。首次健康请求成功，后续请求返回同版本 503，并写入可归类的应用错误日志。通过已安装健康 Worker 和 PostgreSQL 核对原容器、原发布、事件及触发序号。以登记的只读 Whiskers 权限通过 Agent 获取状态、发布和归类后的日志证据，记录诊断摘要及建议。
2. 使用人类门户受众令牌确认该诊断的修复提案。此批原生夹具调用正式授权服务，C3-D 接入可操作门户和外部 MCP。核对任务与事件唯一关联，启动实际已安装 Worker，在一次性 VM 复现原版，读取限定源码并提交受限差异。复用正式 Agent 的工具协议和检查点，确认原版本和补丁以独立 VM 结算。
3. 对新的候选重新审批。通过现有 Registry 和 Komodo Worker 写入，在受保护入口独立核对新实例、新镜像摘要、新版本和连续两次健康响应，确认相关事件关闭。验收同时检查错误指纹、普通 API 令牌无法代替门户确认、重复确认幂等以及缺少发布审批时的排队边界。

工件记录关联 ID 与摘要、授权拒绝、VM 清理、Komodo 两个版本的发布回执及 Whiskers 归类日志。范围分别注明真实 PostgreSQL、KVM、Komodo、Whiskers、Registry、Keycloak 入口、平台签名 OIDC 身份夹具及 Anthropic 协议的确定性模型。C3-D 沿用同一关联模型交付双语门户、外部 MCP 和停止入口。
