# P3-C3-D3b · 健康事件的原生接口联验

在 [#133](https://github.com/MaLaNg116/itervane/pull/133) 的双语门户交互和 [#129](https://github.com/MaLaNg116/itervane/pull/129) 的原生双版本发布基础上，用同一次实际故障核对门户所用的 HTTP 入口与外部 MCP。 [C3 总计划](p3-c-operations-incidents.md) · [开发与运行闸门](../decisions/0001-development-and-runtime-gates.md)

1. 托管 KVM 保留标准应用的固定缺陷提交。先发布原版，再用真实 Komodo、Keycloak 保护入口、Health Worker 与 Whiskers 读面记录同实例的 503、事件和正式诊断。
2. 比对中英文的 HTTP 和外部 MCP 事件、诊断、源码和关联任务。普通 API 身份与错误发布绑定均无法停止自动诊断。门户所有者绑定同一事件确认，二次请求返回原回执。随后继续采样实际 503，原事件保留且调度返回人工停止。
3. 外部 MCP 从同一诊断准备提案。门户所有者确认原提案指纹，拒绝普通接口身份及陈旧指纹。重复确认读取同一正式任务。对照 HTTP 和 MCP 检查关联关系，并以并发与失效授权的真库用例补充协议负例。
4. 隔离 Runner 在固定源码复现故障，受控修改后由另一台 VM 复验，继续使用正式 OCI 归档、独立发布审批和下游核对。新版本通过两次独立采样，原事件有目标更换关闭凭据。

场景使用签名 OIDC 测试令牌区分平台身份、真实 Keycloak 守护应用入口，以及确定性的 Anthropic 协议模型夹具。门户浏览器交互和完整安装运行在各自批次提供证据。托管回执纳入事件、停止、诊断、两个源码代次及两版发布的关联验证。
