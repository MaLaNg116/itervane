# P3-C2b2 · 处置调度与执行权

接续 #88 的持久化准入，沿用全局执行槽和已登记环境。在任务、队列和持久化处置记录之间建立可核对的关联。 [处置准入计划](p3-c-operations-execution-admission.md) · [前置 PR](https://github.com/MaLaNg116/itervane/pull/88)

| 工作 | 验收 |
| --- | --- |
| 事务入队 | 为已获批处置登记独立的运维任务与当前代次。处置、运维任务和 PostgreSQL 队列在一个事务内提交。原诊断继续保留其证据和结算状态。重复唤醒只能指向同一处置及当前代次。 |
| 领取与续约 | 复用现有执行槽、租约时钟及防护代次。已占用的槽继续协调开发、发布和运维。领取重新核对当前批准、授权、环境、目标发布和已登记能力。 |
| 发送意图和恢复 | 记录将要发出请求的批准版本与执行代次，提交事务后才调用下游。仅领取阶段失败可重新安排。存在发送意图时，后继 Worker 进入结果核对，保留环境占用。挂起原生审批时释放全局槽并保留当前批准关联。 |
| 审批撤销 | 处置派发前的撤销与记录和队列一致提交。并发撤销或换绑阻断正在准备的动作。进入结果核对后以实际证据结算，保留可能存在的原生批准与操作轨迹。 |

验证使用真实 PostgreSQL，覆盖事务失败、重复投递、开发发布与运维争用同一执行槽、租约超时、旧执行者、撤销竞态和结果未知的后继接管。C2c 将这些边界接到真实 Whiskers 和独立健康验证。

先交付事务入队、待派发撤销和过期关闭，再交付领取、续约、发送意图和接管。队列唤醒绑定处置、任务与代次，复用原有运维角色。调度和健康证据由各自的验收记录证明。

## C2b2b 领取、发送意图与接管

接续 #89。领取与发送意图分别核对当前批准、发起人与批准人授权、环境和已发布目标。执行事务先锁全局执行槽，再锁诊断任务、环境和处置任务。撤销和发布准入仍用同一个环境锁。业务事务提交时，当前唤醒和任务状态保持一致。

| 场景 | 验收 |
| --- | --- |
| 正常领取 | 唤醒必须匹配处置、任务、运行和代次。安装范围错配或全局槽被占用时保留任务，并为后续领取安排新唤醒。租约以数据库时钟续约。 |
| 发送前失权 | 批准撤销或过期原子关闭待派发运行。权限或映射变化阻断领取和发送意图登记。后继执行者能清理已关闭的槽，原执行者不能继续写。 |
| 发送意图 | 唯一记录绑定批准版本、提案指纹、任务代次、Worker 和 fence。当前执行者只获准登记一次。与原生请求相关的审批回执将在 C2c 接入。 |
| 崩溃恢复 | 只有已领取的任务能重新排到派发队列。存在发送意图时，后继执行者只领取核对任务。撤销和到期仍保留该环境的互斥占用，结算由下游证据驱动。 |

使用真实 PostgreSQL 测试争用、旧 fence、领取后崩溃、新旧批准、期限、换绑和单一发送意图。C2c 在原生确认和健康验证一起通过后接入 Worker 的真实写入。
