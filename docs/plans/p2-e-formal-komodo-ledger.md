# P2-E-C4-B · 正式 Komodo 派发记录与恢复

接续已批准候选在 Registry 的同摘要证明、版本化 Komodo 目标及受限适配器。继续使用正式发布操作、执行槽、环境锁、事件及步骤记录。 [C4 目标与派发计划](p2-e-formal-komodo-target.md) · [适配器 PR #50](https://github.com/MaLaNg116/itervane/pull/50)

## C4-B1 · 固定前置证据与持久化意图

1. 进入下一步前，确认同一操作当前处于 Registry 已核验阶段。恢复过程可能保留已确认的历史证据，必须先核对本轮结果并恢复到已核验阶段。旧 fence 及只读 Registry 恢复权不授予下游写权。
2. 复用正式发布步骤表，加入两种相互独立的 Komodo 步骤，每种对同一操作最多一个意图。配置步骤绑定当前运行配置摘要、原镜像、批准镜像、目标版本和提交人；派发步骤还需要同一操作的配置确认。挂接后保留原 fence、服务身份、目标和摘要。限制文档长度及字段，状态和证据变更在事务内写入双语事件。
3. 在事务和数据库约束中核对候选、批准有效期、环境占用、目标、上游证明及待执行步骤。进入网络写操作前使用当前执行权再核对。在当前步骤仍未核对的情况下，新的持有者只能读实际状态。

验收使用真实 PostgreSQL，覆盖从待核对跳过上游、过期或撤销、错误目标、竞争认领、重复准备、错配证据和过期 fence。现有 Registry 及旧的审批记录继续按原格式校验。

## C4-B2 · 接续 Worker 与只读恢复

1. 从 Registry 完成后移交给正式 Komodo 消费者，保留操作和环境占用。需要由新 Worker 接续时，重新验证目标和批准并获得对应步骤的有效执行权。先读实际配置，再分别提交受限配置和派发意图并调用对应适配器。每个已提交意图至多发送一次写请求。
2. 配置写入的结果不明时，回读当前配置摘要、目标和镜像。确认配置后仍需重新校验权限才能派发。通过原生更新 ID 核对派发结果，保留独立证据；没有可靠更新 ID 或锚点时，保留环境占用并进入人工核对。拒绝再次发送同一步写请求。
3. 确认与读回采用受限观察权，允许在原批准撤回或到期后处理已发送结果。只读重查有明确的持久化次数上限，进程中断也计入预算。取消停止后续写入，遗留的已发送操作走核对，明确区分实际结果和用户的取消请求。

用真实临时 Core、Periphery、Registry 和固定候选覆盖写请求后进程中断、已知和未知更新 ID、只读恢复、过期审批及双重派发阻断。保存固定源码、双语事件、原生更新和实际结果的关联证据。

## E-D 的独立出口

Komodo 更新成功只确认下游派发结果。E-D 再核对实际运行版本和配置、保护入口及健康检查，同时验证失败后的环境占用和升级。通过完整 P2 运行验收后再启用正式发布。
